# 台股投資決策輔助系統

雙擊桌面圖示 → 瀏覽器開啟儀表板 → 看今天有沒有要處理的事。

核心設計原則只有一句：**規則寫在系統裡，不寫在腦袋裡。**
系統負責計算與提醒，出場與否永遠由你人工確認。

## 第一次使用

### macOS

**在 Finder 裡雙擊 `launch/安裝.command`**，然後照著畫面走。

### Windows

**雙擊 `launch\win\安裝.bat`**，然後照著畫面走。

`launch/` 最外層那幾個檔案（`.app`、`.command`、`install_daily.sh`）**是 macOS 專用的**，
在 Windows 上點了不會有反應。Windows 的東西全部在 `launch\win\` 底下。

還有一個容易踩的地方：**Windows 內建的 `python` 指令通常是 Microsoft Store 的空殼**，
執行起來直接 exit 49，不會有看得懂的錯誤訊息。能用的是 **`py`**。
文件裡寫 `python3 xxx.py` 的地方，在 Windows 上都請改成 `py xxx.py`。
安裝腳本會自己找出可用的那一個，不需要你處理。

### Windows

沒有 `.command` 那種一鍵安裝，照下面三步走（PowerShell）：

```powershell
$env:PYTHONUTF8 = "1"        # 見下方說明，少了這行 pip 會直接失敗
py -m pip install -r requirements.txt
py tests\test_signals.py; py tests\test_store.py   # 確認裝好了
```

然後雙擊 `launch\dashboard.bat` 就會開儀表板（等同 macOS 的「投資儀表板」）。
想要桌面捷徑就對它按右鍵「傳送到 → 桌面（建立捷徑）」。

**Windows 特有的三個坑**，踩過才知道，先寫在這裡：

| 症狀 | 原因與解法 |
| --- | --- |
| `python` 執行後沒有任何輸出，exit code 49 | 那是 Microsoft Store 的空殼別名，不是真的直譯器。**一律用 `py` 啟動器**，或直接指定安裝路徑。 |
| `pip install -r requirements.txt` 噴 `UnicodeDecodeError: 'gbk' codec` | `requirements.txt` 有中文註解，pip 用系統 cp950/cp936 去解碼。先設 `PYTHONUTF8=1` 就過了。 |
| 改了 `.bat` 之後出現 `'x' is not recognized` | `.bat` 必須是 **CRLF 換行**。Git Bash 的 heredoc 和 `sed -i` 都會寫成 LF，cmd.exe 會把 `\|\|` 那類行解析壞、而且靜靜地走錯分支。要改就用 PowerShell 或設好 `core.autocrlf` 的編輯器。 |

`launch\dashboard.bat` 和 `launch\daily_run.bat` 內容刻意保持純 ASCII，
就是為了避開第三個坑——中文只出現在 Python 的輸出，由 `chcp 65001` 加 `PYTHONUTF8` 處理。

停損線防的是「虧太多」，那一段防的是「抱著一個已經錯掉的理由」。

## 研究筆記

儀表板的「研究」分頁，或 `python3 src/research.py`。

用來回答「我到底買了什麼、現在在發生什麼」——
跟「今日」那頁的「今天要不要動作」是兩種完全不同的閱讀節奏，所以分開。

### 報告分成三塊，而且標示得很清楚

| 區塊 | 是什麼 | 可信度 |
| --- | --- | --- |
| **價格在說什麼** | 從日 K 直接算的：各期間報酬、一年區間位置、起漲點、量能、波動度、相對大盤、同業比較 | 可自行驗證 |
| **這家公司在做什麼** | 產業、供應鏈位置、營收跟著什麼跑、該追蹤什麼、這個產業最常見的誤判 | 人工整理，**會過時** |
| **要你自己去查** | 系統沒有資料源的部分，附上該問什麼問題 | 系統不知道 |

### 它不能做什麼（重要）

**它不能告訴你「為什麼」漲。**

價格會動是因為新聞、財報、法說會、法人買賣、總體經濟——
這套系統**一個都沒接**。它只能告訴你**漲勢的形狀**：
漲了多久、漲幅多少、量能有沒有配合、
是整個產業一起漲還是它自己獨走、現在的價格在過去一年的什麼位置。

形狀本身就很有用。舉例來說，報告會這樣寫：

> 同業近 3 個月：南電 +25%、金像電 +2%（平均 +13%），它自己 +32%
> —— **它明顯走得比同業強**。同一個產業裡只有它大漲，
> 通常代表市場在反映這家公司自己的事（訂單、財報、題材），
> 而不是整個產業的景氣——那就更需要去查清楚那件事是什麼。

它把「該去查什麼」變得具體，但查還是要你自己查。

### 名詞辭典

不熟 PCB、封裝、CoWoS、ABF 載板、本益比、除權息這些詞？辭典有 50 條，
每一條都是「一句話講完 + 多一點背景 + 為什麼你會在新聞裡看到它」。

研究頁下方可以直接搜尋，或用命令列：

```bash
python3 src/research.py --term CoWoS
python3 src/research.py --term 載板      # 別名也查得到（ABF → IC 載板）
python3 src/research.py --glossary       # 印出全部
```

每檔股票的報告下方也會自動附上它相關的名詞。

### 知識庫在哪、怎麼改

```
config/glossary.yaml   名詞辭典（50 條）
config/sectors.yaml    產業地圖（57 檔）
```

兩份都是人工維護的純文字檔，看得懂就改得動。
買了新標的就照格式加一筆，找不到的代號不會出錯——報告照樣產生，只是少了背景那一段。

這兩份檔案**刻意只寫變化很慢的東西**（商業模式、供應鏈位置、該看什麼指標），
不寫市占率、客戶名單、目標價、財測。那些寫下來三個月就過期，
而過期的資料比沒有資料更危險，因為你會以為它還準。

## 監控層要監控誰

「今日」頁與日報上的持股，來源由 `config/positions.yaml` 最上面的 `source` 決定：

| `source` | 監控對象 | 適合什麼時候 |
| --- | --- | --- |
| `manual` | 你自己填在 `positions.yaml` 的持股 | 你自己下單、自己記帳 |
| `engine` | 程式交易引擎的部位帳本（`data/paper_state.json`） | 想直接看「這套規則現在抱著什麼」 |
| `both` | 兩邊都看，各自標示來源 | 過渡期，想同時對照 |

設成 `engine` 之後，每次成交不用再回頭手動編輯 YAML。
這不只是省事：**手動登記漏一筆，畫面上不會有任何地方看得出來**——
損益、停損線、投組總覽全都照樣算得出數字，只是全部是錯的。

### 停損線用誰的規則（重要）

引擎部位的停損停利價，一律由**引擎自己的規則**算
（`config/paper.yaml` 的 `strategy` 那一段，ATR 模式時是「進場價 ± N × 進場當下的 ATR」），
**不套用 `strategy.yaml` 的 `rules` 百分比**，個股例外規則也不套用。

理由是這兩套參數本來就獨立。如果讓監控層用自己的百分比重算，
畫面上會出現一條「引擎明天根本不會照它執行」的停損線——
那比沒有停損線更危險，因為它看起來完全正確。
每一條線旁邊都會標明它是怎麼來的（例如 `2×ATR(14)＝24.00 元`）。

`source: engine` 時，儀表板的「持股異動」表單會被停用。
不擋的話那些表單還是會寫進 `positions.yaml`，但畫面完全不會變——
讓人以為做了某件事而其實沒有，比擋下來難救得多。
`positions.yaml` 裡原本的資料仍然保留，改回 `manual` 就會回來。

⚠️ 這一切仍然**沒有連接任何券商**。引擎的「自動進出場」發生在它自己的帳本裡，
`source: engine` 只是換了監控對象，不代表有任何一張單真的送出去。

## 模擬倉（paper trading）

除了監控你手上的持股，系統還可以**自己跑一套 1～2 週的波段策略**——
產生進出場決策、算進交易成本、記錄每一筆，然後在日報裡跟你報告。

**全程是虛擬的。沒有連接任何券商，不會送出任何真實委託。**
目的是先累積幾個月「這套規則實際上會做什麼決定」的證據，再決定要不要用真錢。

### 開始跑

**1. 補歷史日 K**（策略要算均線，需要至少 61 根 K）

```bash
python3 src/history.py --months 24
```

預設補「持股 + 觀察清單」裡的所有代號。

**只會抓缺的月份**——過去的日 K 不會再變，已經有的直接跳過，
所以第一次大約兩到三分鐘，之後每次只補最近兩個月，幾秒就好。
每抓完一個月就存檔，中途 Ctrl+C 不會弄丟已經抓到的部分，重跑會從缺的地方接下去。
執行時會逐月印出進度和剩餘時間。

```bash
python3 src/history.py --status      # 看目前累積到哪，以及中間有沒有缺
python3 src/history.py --fill-gaps   # 補中間缺掉的月份
python3 src/history.py --force       # 連已有的月份也重抓
python3 src/history.py --months 12   # 只補 12 個月（第一次回測夠用）
```

### 中間缺月份會怎樣

抓到一半被中斷、或端點限流導致某幾個月失敗時，檔案會留下破洞——
**看起來涵蓋兩年，中間卻是空的**。這不會報錯，但會讓指標算錯期間。

`--months 12` 只檢查最近 12 個月，更早的破洞永遠不會被發現。
所以 `--status` 會另外檢查整段已涵蓋的範圍：

```
2330: 2024-09-02 ~ 2026-08-19  共 294 根  ⚠️ 缺 2024-12、2025-01 等 9 個月
```

看到就跑 `--fill-gaps`。它只補缺的那幾個月，不會整段重抓。

**它怎麼知道一個月「應該」有幾根？** 不是寫死的門檻——
那樣會踩到農曆年：2026 年 2 月因為春節休市（2/12–2/20）真的只有 12 個交易日，
用固定門檻會把每一檔都標成「缺 2026-02」，而且補了也不會消，
因為那個月本來就是完整的。颱風假、補班日也一樣。

改成從資料本身推導：**所有追蹤標的中該月最多的那個根數，
就是那個月真正的交易日數**。只要有任何一檔抓齊了，基準就是對的。
不需要維護假日表，農曆年和颱風假全部自動處理。

研究筆記本身也防這件事：期間報酬一律用**日曆天**算，
不是「往回數 250 根 K」。有破洞時往回數 250 根拿到的可能是兩年前的價格
（實測橫跨 648 天），而報告上仍寫著「1 年報酬」。
改用日曆天之後，缺資料的期間會顯示「—」，不會給你一個標錯期間的數字。

### 為什麼不是「抓 N 次 × 等 N 次」

這兩支端點偶爾會慢到好幾秒才回應。如果寫成「送出 → 等回應 → 停一下 → 下一個」，
總時間會是 **次數 ×（延遲 + 間隔）**，延遲才是大頭，間隔完全不是瓶頸。

所以這兩件事被拆開了：

- **多久送一次請求**：全域限速，對端點的禮貌，預設 4.5 秒
- **等回應**：交給併發蓋掉，預設 3 檔同時進行

總時間變成 `max(次數 × 間隔, 延遲 ÷ 併發數)`，跟延遲幾乎脫鉤。
**多開 worker 不會讓請求變密**，限速器仍然管著發送節奏，
只是允許更多請求同時在路上等回應。

要調的話：

```bash
INVEST_FETCH_DELAY=8     python3 src/history.py   # 發送間隔（秒）
INVEST_FETCH_WORKERS=10  python3 src/history.py   # 同時抓幾檔
INVEST_FETCH_TIMEOUT=20  python3 src/history.py   # 單次請求逾時（秒）
```

> **間隔只能往上調，不要往下。** 預設的 4.5 秒是踩過坑訂的：
> 原本是 1.2 秒，2026-08-27 回補到一半被 www.twse.com.tw 擋掉整個 IP
> （「因為安全性考量，您所執行的頁面無法呈現」），封鎖持續超過 50 分鐘。
> 被擋之後才調慢是沒用的——封鎖綁的是 IP，只能等它自己解，
> 而且上市股的逐月歷史沒有第二個端點可以繞。不建議低於 3 秒。
>
> 如果進度裡出現大量「失敗」，那是端點在擋你，把間隔調高而不是調低；
> 若連 428 或整頁 HTML 都出來了，就是已經被擋了，停手等一陣子再跑。

### 同時跑兩個回補會怎樣

不會怎樣，跑就是了。

歷史檔案的寫入有檔案鎖與原子寫入保護，所以下面這些情況都是安全的：

- 手動回補時剛好碰上 15:00 的每日排程（`main.py` 也會寫同一批檔案）
- 兩個回補行程並行
- 寫到一半按 Ctrl+C 或斷電

任何時刻讀到的都是完整的檔案，不會是寫到一半的狀態。

**2. 先回測，看這組參數在過去會做什麼**

```bash
python3 src/backtest.py
python3 src/backtest.py --verbose      # 印出每一筆成交
```

**3. 之後每天跑 `src/main.py` 時模擬倉會自動前進一天。**

在 `config/paper.yaml` 把 `enabled` 改成 `false` 就完全關掉，
或單次跳過：`python3 src/main.py --no-paper`。

### 策略在做什麼

進場要**四個條件同時成立**（收盤時判斷，隔日開盤成交）：

| 條件 | 為什麼 |
| --- | --- |
| 收盤站上 60 日均線 | 不逆勢接刀 |
| 收盤站上 20 日均線 | 中期動能還在 |
| 突破前 20 日最高價 | 這就是進場觸發 |
| 近 20 日均量 ≥ 500 張 | 買得到、賣得掉 |

出場四選一，**停損優先**：停損 −8%、停利 +15%、移動停損（預設關閉）、
或抱滿 15 根 K 還沒觸發就時間出場。最後這條是「波段」的定義——
沒有它，一檔不上不下的股票會變成你根本沒打算做的長期投資。

### 停損寬度：固定 % 還是跟著波動度走

`config/paper.yaml` 的 `stop_mode` 有兩個選擇：

| 模式 | 停損怎麼算 | 適合 |
| --- | --- | --- |
| `pct`（預設） | 固定 −8%，每檔一視同仁 | 波動度接近的一組標的 |
| `atr` | 進場價 − 2 × ATR(14) | 波動度差很多的一組標的 |

**ATR（平均真實區間）就是「這檔一天通常會動多少錢」**，單位是元不是百分比，
而且會把跳空算進去——一根開盤就跳空的 K，只看高低差會低估它的波動。

為什麼會想換：固定 8% 對每檔都一樣，但一檔日常波動 1% 的電信股
和一檔波動 10% 的航運股，8% 的意義完全不同。研究筆記會直接幫你換算：

> ATR(14) **7.18 元**（現價的 10.1%，也就是「一天通常會動這麼多」）——
> **這檔的 8% 停損太緊**，只有 0.8 倍日常波動，很容易被雜訊掃出場。

> ATR(14) **0.94 元**（現價的 1.0%）——8% 停損等於 8.3 倍日常波動，**偏寬**，
> 真的觸發時已經賠了不少。

停損寬度在**進場當下就固定**，之後不會隨 ATR 變動——
會移動的停損線沒辦法讓你在進場前算出這筆最多會賠多少。
每筆成交紀錄都會寫下當時用的基準（`2×ATR(14)＝10.00 元`），覆盤時看得出來。

設成 `atr` 但進場時歷史不足以算 ATR 的話，會退回固定百分比，
**並在紀錄裡註明**——安靜地換一套規則是最糟的做法。

### 三個刻意保守的設定

1. **成交價用隔日開盤價**，不是當日收盤價。收盤價是你做決定當下才知道的數字，
   拿它下單等於偷看未來，回測會漂亮得不像話。
2. **交易成本照實算**：手續費 0.1425%（可設折扣、最低 20 元）買賣各一次，
   賣出再課 0.3% 證交稅。來回大約 **0.47%**。停利設 15% 而不是 3%，
   一部分原因就在這裡。
3. **只買整張**。零股的成本結構和流動性不一樣，不混在一起模擬。

### 日報會告訴你什麼

- 今天成交了什麼、成交價多少、手續費和稅各多少
- 明天開盤要下什麼單、理由是什麼
- **其他標的今天為什麼沒買** —— 是趨勢不對、沒突破、量太小、
  名額滿了，還是資金不夠。這段最容易被省略，但它才是你之後調參數的依據。

### 產出

```
data/history/          歷史日 K（衍生資料，不進版控，隨時可重建）
data/paper_state.json  當前虛擬現金、持股、待執行委託
data/paper_trades.jsonl 每一筆成交，含完整的進出場理由  ← append-only
data/paper_equity.jsonl 每日淨值曲線                    ← append-only
```

`paper_trades.jsonl` 每一筆都記著當初進場時四個條件各是什麼數字。
兩個月後你不會只看到「買了 2330」，而是看到「當時它站上 60 日均線 116.94、
突破前 20 日高點 133.90」——那才有辦法判斷規則本身對不對。

### ⚠️ 讀績效數字之前

- **少於 30～50 筆交易的統計沒有意義。** 勝率 70% 但只有 6 筆，那是雜訊。
  報告和回測都會在樣本不足時主動提醒你。
- **不要看到虧損就調鬆停損、看到獲利就調緊停利。** 那是最常見的自我欺騙路徑，
  你會得到一組在歷史上很漂亮、對未來毫無預測力的參數。
  要改就在 `config/paper.yaml` 的 changelog 留一行。
- 回測**沒有**模擬「買不到」的情況，假設你要的張數在開盤都成交得掉。
  對日均量 500 張以上、每次只買 20% 部位的規模還算合理，資金放大後會失真。

## 訊號說明

| 訊號 | 意義 |
| --- | --- |
| 🔴 觸發停損 | 收盤 ≤ 停損線，規則判定該出場 |
| 🟢 觸發停利 | 收盤 ≥ 停利線，規則判定該出場 |
| 🟠 接近停損 | 距停損線 3% 以內（預警） |
| 🔵 接近停利 | 距停利線 3% 以內（預警） |
| ⚪ 續抱 | 在區間內 |
| ⚓ 核心部位 | 不套用停損停利（長期持有的 ETF 等） |
| ❔ 無行情 | 當日查無報價（停牌、代號錯誤） |

「距停損」／「距停利」= **現價要再變動多少 % 才會碰到那條線**。
距停損 `−14%` 代表還要再跌 14% 才停損；轉為正數代表已經跌破。

### 停損基準

- **以成本價計算**（預設）：成本 100、停損 10% → 停損線固定在 90。
- **以進場後最高價計算**（移動停損）：成本 100、最高漲到 150 → 停損線變成 135，鎖住部分獲利。

移動停損的歷史高點來自每日紀錄，剛啟用的前幾天會退化成用成本價計算，儀表板會標註。

`data/history/` 之所以進版控，是因為重建它要 55 檔 × 24 個月、
被限速在 4.5 秒一次，跑快兩小時而且一直打證交所——但整包才 1 MB 出頭。
`data/raw/` 則相反：一個交易日就 4.5 MB，一年超過 1 GB，
需要時用 `python3 src/history.py --from-raw` 從本機存檔離線重建。

### `signals.jsonl` 是最重要的產出

每天一行，記錄當天的**規則參數**、價格、停損停利線、訊號判定。
因為它記錄了「當天用的是什麼參數」，兩個月後你可以驗證自己有沒有在過程中偷偷調鬆停損。
沒有這份紀錄，你會拿到一份回頭看很合理、但什麼都證明不了的資料。

**不要回頭編輯它。** 需要修正就 append 新的一行。

## 測試

```bash
python3 tests/run_all.py          # 一次跑完（失敗時結束碼 1，可掛排程或 git hook）
python3 tests/run_all.py -v       # 連每一項 PASS/FAIL 都印出來
```

想單獨跑某一支：

```bash
python3 tests/test_signals.py     # 停損停利判斷的分支、移動停損峰值的起算日
python3 tests/test_monitor.py     # 監控層接引擎部位：停損線必須跟引擎一致
python3 tests/test_store.py       # 透過介面改設定不會弄壞 YAML
python3 tests/test_paper.py       # 交易成本、進出場訊號、成交、名額上限、
                                  #   累計績效的來源、狀態檔壞掉的行為
python3 tests/test_history.py     # 日 K 存取、民國日期、TWSE 解析
python3 tests/test_backtest.py    # 回測引擎的不變式（合成資料，不連網）
python3 tests/test_research.py    # 指標計算、ATR、名詞查詢、知識庫完整性
```

全部不需要 pytest，也不連外網，跑完會印 `全部通過 ✅` 或以非零狀態結束。

**改了 `src/` 底下任何檔案之後請先跑過**——
規則被改壞是沉默的：報告照樣產生、數字照樣漂亮，只是錯的。

`test_backtest.py` 檢查的不是「策略賺不賺錢」（合成資料證明不了那件事），
而是**引擎有沒有作弊**：現金會不會變負的、部位有沒有超過上限、
淨值等式對不對、成交價是不是真的來自隔日開盤。
只要有一條不變式被破壞，後面所有績效數字都不用看了。

`test_research.py` 除了驗算指標，還會把 `sectors.yaml` 引用的名詞
跟 `glossary.yaml` 交叉比對一遍。你之後加標的時打錯一個字，
報告不會壞掉——它只會安靜地少一段，這支測試就是為了讓錯字當場被抓出來。

## 資料源

| 市場 | 端點 | 費用 |
| --- | --- | --- |
| 上市 | `openapi.twse.com.tw/v1/exchangeReport/STOCK_DAY_ALL` | 免費、免金鑰 |
| 上櫃 | `tpex.org.tw/openapi/v1/tpex_mainboard_daily_close_quotes` | 免費、免金鑰 |

兩支都是「一次回傳全市場」，追蹤 3 檔或 300 檔都只打兩次 request。內建 3 次重試與 30 分鐘快取。

歷史日 K 另外走「逐檔月報表」端點（`src/history.py`），
上市與上櫃都支援，`--market auto` 會自己判斷該打哪一支。
這兩支是網頁後端 API 而非正式開放資料，改版風險比較高，
所以解析一律用**欄位名稱比對**而不是寫死索引，而且忽略名稱裡的空白——

> 上櫃回傳的日期欄位實際上叫「**日 期**」，中間有一個空格，
> 同一份回應裡其他欄位卻沒有。用子字串比對會找不到它，
> 然後整個月靜靜地變成零根 K：不拋例外、沒有錯誤訊息，只是均線少一段。
> `tests/test_history.py` 用兩個市場的實際欄位做迴歸測試，就是為了這個。

還有自我檢查：

```bash
python3 src/history.py --self-test
```

它會對兩個市場各抓一次、印出實際回傳的欄位，解析不出來時直接告訴你。
（工具箱選單裡的「🩺 檢查資料源是否正常」就是跑這個。）

⚠️ 這是**收盤後**的資料，不是即時報價。系統定位是盤後決策，不是當沖。
